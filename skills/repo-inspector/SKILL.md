# Repo Inspector

Two-mode Git repository analyzer for onboarding unfamiliar codebases and auditing repositories prior to public GitHub release.

## When & Modes

- **Mode 1 — Codebase Onboarding:** GitHub/Git URL or local repo path asking what the project does, how it works, entry points, dev/test commands, or first-contribution guidance (GSoC, LFX, hackathons).
- **Mode 2 — Pre-Release Polisher:** Preparing a Rust, Go, Python, WebExtension, or CLI repo for GitHub publishing (`release kontrol`, `githuba yuklemeden once`, `pre-flight check`).

## Workflow

### Mode 1 — Codebase Onboarding
1. Identify repo archetype (Monorepo, single service, CLI, library) and build manifests (`Cargo.toml`, `go.mod`, `pyproject.toml`, `package.json`, `Makefile`).
2. Run `python3 /workspace/scripts/agent_doctor.py code-graph <target_dir>` on local directories (or inspect manifests on remote URLs) to map entry points (`main.rs`, `cmd/`, `main.go`, `src/index.ts`, `app/main.py`), symbol inventory, module import edges, and test suites.
3. Extract exact install, run, and test commands from `Makefile`, `README.md`, manifests, or `.github/workflows/`.
4. Map a 3-step data/request flow and 2–3 starter files for first contributions. Append to `reports/repos.md` only if requested.

### Mode 2 — Pre-Release Polisher
1. Detect project stack at repo root and audit:
   - **Git & File Hygiene:** `.gitignore` covers build/cache/secret files (`target/`, `dist/`, `bin/`, `__pycache__/`, `.env`, `.DS_Store`); no leaked keys or hardcoded local paths; shell/install scripts have executable permissions (`chmod +x`).
   - **Deep Logic & Security Pass (Elephant-Goldfish Model):** Clear tunnel-vision like a goldfish and inspect specs, entry points, privileged helpers, and network/shell boundaries fresh—assuming the code was generated by a weaker model—hunting subtle logic bugs, race conditions, unverified binary downloads, or permission leaks linters miss.
   - **Scope & Bloat Audit (`ponytail` YAGNI Check):** Flag dead code, unused abstractions, speculative over-engineering, and shallow pass-through wrappers before release.
   - **Build & Tests:** Local tests and linters pass (`cargo test`, `go test ./...`, `pytest`).
   - **CI/CD & Metadata:** Package metadata (`version`, `license`, `repository`), `LICENSE`, and `.github/workflows/` release pipelines/target architectures.
   - **Documentation:** Clear, professional English `README.md` (Features, Installation, Usage, License).
2. Return findings with exact copy-paste fix commands.

## Output

Language matches the user.

- **Mode 1:** Compact card with `# [Repo Name](URL)`, `Dil & Runtime / Paket Yöneticisi / Mimari Tip`, `Dizin Yapısı & Giriş Noktaları`, `Geliştirici Komutları` (`Kurulum`, `Çalıştırma`, `Test`), and `Katkı & Başlangıç Rehberi` (`Özet Akış`, `İlk İncelenecek Dosyalar`, `Dikkat Edilmesi Gerekenler`).
- **Mode 2:** Compact checklist `# Pre-Flight Release Raporu: [Repo Adı]` (`Proje Tipi`, `Yayın Durumu: HAZIR | DÜZELTME GEREKİYOR | YAYINLANAMAZ`, checklists for `Git & Dosya Hijyeni`, `Derleme & Test`, `CI/CD & Metadata`, `Dokümantasyon`, and `Gerekli Düzeltme Komutları`).

## Constraints

- Read-only inspection by default; never modify source code, force-push, or run destructive git commands automatically.
- Never invent file paths, commands, or test results (`Veri bulunamadı` when absent).
- Ensure public-facing README recommendations are in clean English and flag any hardcoded local machine paths before pushing.
